Tarefa: Ice multiplataforma (Python e Java)
Repositório: https://github.com/LuisFcarmo/sistemas_distribuidos (pasta ice-multiplataforma)

Usei a interface Printer da tarefa anterior e mantive o mesmo arquivo Printer.ice para os dois lados. Gerei os stubs com slice2java e slice2py e montei os dois cenários: cliente Java falando com servidor Python, e cliente Python falando com servidor Java. Os dois rodaram sem problema, até com acento nas strings.

O que mais me chamou atenção foi o quanto o middleware tirou de trabalho. Se eu tivesse feito isso direto com sockets, precisaria combinar o protocolo na mão e escrever o mesmo código duas vezes, uma em cada linguagem. O TCP só entrega bytes, então eu teria que decidir onde cada mensagem termina, como mandar inteiros e strings (codificação, ordem dos bytes), como avisar um erro e como identificar qual operação está sendo chamada. Foi mais ou menos o que fiz na calculadora com sockets, só que lá os dois lados eram Python. Com duas linguagens, qualquer mudança, tipo um método novo, vira mexer nos dois parsers, e se um deles ficar diferente o problema só aparece na hora de rodar.

Com o Ice isso fica concentrado no .ice. O compilador gera o proxy e o skeleton, então o cliente chama printer.add(35, 7) como se fosse uma chamada local e nem sabe em que linguagem o servidor está. Trocei Java por Python de um lado e não precisei mexer em nada do outro. Serialização, conexão, threads de atendimento e exceções remotas já vêm resolvidas. E se eu esquecer de implementar algum método depois de alterar o contrato, o próprio compilador reclama.

Em compensação tem coisa que pesa. Os dois lados dependem do runtime do Ice, e precisei garantir a mesma versão (3.7.6) em Java e em Python. Também é preciso aprender os conceitos dele (communicator, adapter, proxy), que não são pequenos para um exemplo simples. Existe um custo de serialização e despacho que um protocolo feito à mão e enxuto evitaria, e é mais chato de depurar porque o tráfego é binário, não dá para olhar a mensagem e entender. Outra limitação é que só quem usa Ice consegue conversar com esse servidor, enquanto um protocolo aberto qualquer cliente implementa.

O middleware também não esconde tudo. O int do Slice tem 32 bits. Testei add(2147483647, 1) no servidor Python e deu erro: o resultado não cabe, a resposta não consegue ser serializada e o cliente recebe ConnectionLostException. Em Java a mesma soma daria overflow sem avisar nada. Então a diferença de representação ele resolve, mas a diferença de comportamento entre as linguagens e as falhas de rede continuam sendo problema meu.

Resumindo: em sockets eu tenho controle total e menos overhead, mas pago refazendo framing, serialização e tratamento de erro em cada linguagem. Com o Ice a integração entre Python e Java ficou bem mais simples, e o preço é depender do runtime e aceitar o que o contrato permite.
